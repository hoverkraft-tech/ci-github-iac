# Validation and releases

## Make and workflow conventions

Follow the [Hoverkraft Makefile](https://github.com/hoverkraft-tech/ci-github-container/blob/main/Makefile)
and [workflow layout](https://github.com/hoverkraft-tech/ci-github-container/tree/main/.github/workflows).
Use annotated Make targets for generated help and a shared `run_linter` helper
for `lint` and `lint-fix`. The container uses Linux amd64, the caller's UID/GID,
and the checkout's absolute path for its workspace. A failed image build stops
the command before linting.

`make help` lists commands. `make lint-fix` applies supported automatic fixes;
`make lint docs/` limits linting to matching paths. Positional filters are accepted
only for lint commands; unknown standalone targets still fail. `make ci` runs
`lint-fix` and unit tests locally. Run the VM lifecycle separately with `make e2e`.

Internal `__main-ci.yml` and `__pull-request-ci.yml` call `__shared-ci.yml`.
Main supports pushes and manual runs; PR CI also supports merge queues. Both
cancel superseded runs for the same workflow and ref. The internal action-test
workflow composes `actions/vm/create`, `test` and `destroy` for success, assertion
failure and startup failure. Consumers compose the same actions in their VM jobs.
Workflows start with `permissions: {}` and grant only the permissions required by
each job. Keep Actions pinned and step names descriptive. The aggregate `checks`
job requires every prerequisite to succeed and is required by branch protection.

## Repository automation

Keep the five Hoverkraft maintenance workflows alongside the CI entrypoints:

- `__greetings.yml` welcomes first-time contributors on new issues and PRs.
- `__need-fix-to-issue.yml` turns fix markers into issues after main pushes, or
  for a manually selected commit range.
- `__semantic-pull-request.yml` validates Conventional Commit PR titles.
- `__renovate.yml` runs dependency updates weekly and on manual dispatch.
- `__stale.yml` manages inactive issues and PRs daily using shared defaults.

The four collaboration workflows reuse the pinned ci-github-common workflows.
Renovate uses the organization's `CI_BOT_APP_CLIENT_ID` Actions variable and
`CI_BOT_APP_PRIVATE_KEY` Actions secret. Its GitHub App must be installed on this
repository with the permissions requested by the token-generation step.
The Lima version is maintained in `actions/vm/create/action.yml`.
Keep the token scoped to this repository and the repository configuration in
`.github/renovate.json`. Dependabot owns Actions and Docker updates; Renovate
owns the configured custom dependency patterns. Schedules become active after
these workflows reach the default branch.

## Validation

Use Node.js 24.8 or later locally. Run `make test` with its built-in test runner for failure,
cleanup, report and action-output contracts, `make lint` for the
Hoverkraft containerized linter, and `make e2e` on a KVM-capable host for actual
VM behavior. PR CI verifies action outputs across successful assertions, failed
assertions and failed startup, without a consumer Makefile. It repeats tests on
the same guest to verify independent reports, copies JUnit and coverage files
after assertion failures, and verifies the shared parser's file list and summary.
Local Make composes
the same JavaScript resource and assertion components. Do not replace a boot check with mocked CLI output.

## Releases and dependencies

Use Conventional Commits and a reviewed pull request. Publish semantic versions
only after CI and consumer validation pass: major for incompatible contracts,
minor for compatible features, patch for fixes. Consumers pin full commit SHAs;
do not move release tags. No release is published during bootstrap.

Dependabot updates Actions and Docker dependencies. Renovate updates Lima and the
documentation CLI. Review the Ubuntu image URL and SHA-256 together against the
official release index when refreshing the fixture; boot the new image before
merging. A dependency proposal is not evidence of compatibility.

Action reference docs are generated by the existing Hoverkraft CI Dokumentor
CLI through `make docs`. Change action metadata and regenerate; never hand-edit
the generated reference. Author usage guidance under docs/usage.

## Action runtime

Use the pinned `actions/github-script` runtime and its injected `core` helpers
for action inputs, outputs and failures. Pass inputs through step environment
variables. Keep each action entrypoint in `index.cjs` beside its `action.yml`.
The YAML script only loads that file from `github.action_path` and passes `core`.
Use relative imports inside the entrypoint for shared VM modules, so a consumer
checkout cannot replace the implementation. Keep those modules executable with Node.js 24
for local validation; no package installation or build is required.
